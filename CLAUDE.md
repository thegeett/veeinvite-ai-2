# VeeInvite — Claude Code Context

AI-native wedding invitation website builder. Couple answers a short quiz → AI picks a layout, generates a coherent visual identity + hero, renders a complete site in under 2 minutes.

## Frontend-design skill — required for all UI work

Every React component, page, or distinctive UI surface in Stream A **must** be scaffolded by invoking the `frontend-design` skill first. Ad-hoc components produce generic AI design; VeeInvite's value is distinctive output. This applies to:

- All `src/app/**/page.tsx`
- All `src/components/**`
- The 4 HTML skeletons in `layouts/`
- The landing page

Does NOT apply to: API routes, renderer, validator, AI prompts (non-visual code).

## Architecture rules — never break these (plan §21)

1. App name is **VeeInvite** everywhere.
2. Never modify layout skeleton files after Phase 1 is complete. Skeletons contain nav + all sections except hero.
3. Hero section is NOT in any skeleton. Generated by Call 3, prepended by renderer.
4. Call 2 designs the entire site as one visual identity. Establishes `globalTokens` once. No section introduces its own palette.
5. Call 3 receives `globalTokens` as hard constraints. Same background, accent, gold, fonts. Full creative freedom on everything else.
6. `theme_json`, `globalTokens`, and `hero_html` are sources of truth. HTML in storage is always derived. Never treat it as canonical.
7. `injectStructured()` always runs LAST in the renderer. Real names/dates/venues always overwrite AI copy.
8. Validator never throws. Bad values get safe defaults. Site always renders.
9. RSVP form structure is never generated by AI. Data-driven via `rsvp_config` (§29).
10. All Claude API calls are server-side only. Never expose `ANTHROPIC_API_KEY` or `SUPABASE_SERVICE_ROLE_KEY` to the browser.
11. `/w/[slug]` returns raw HTML. Not wrapped in Next.js layout. Standalone wedding site.
12. AI never sets layout CSS properties — `display`, `position`, `flex-direction`, `grid-template-columns`, `overflow`, `width`, `height` — always owned by skeleton CSS.
13. Nav anchor IDs are fixed: `#story`, `#events`, `#rsvp`, `#gallery`, `#faq`. Hero must not add a nav link for itself.
14. Layout switching reuses existing tokens. Applying existing `theme_json` to new skeleton — no AI call.
15. Design summary replaces raw style history in edit prompts (prevents drift).

## Cultural profile system (plan §26)

The single source of cultural truth is `src/lib/cultural-content-library.json`. It defines:

- 14 cultures/sub-regions: western, hindu_indian (punjabi/gujarati/bengali/tamil/marathi/telugu/kannada/kerala_malayali/marwari_rajasthani/jain), sikh, muslim (south_asian_muslim/arab_muslim/west_african_muslim), chinese, jewish, nigerian_yoruba, nigerian_igbo, latin_american_catholic
- Per culture: content items (with `section` placement), ceremonies (default + sub-region overrides + additional), designGuidance, copyTone, copyGuardrails
- `copyGuardrails` is a HARD RULE block injected into Call 2 and Call 3 prompts. For Tamil: no Sangeet/Pheras/Baraat. For Muslim: no alcohol or human figures. For Jewish: Chuppah time must be prominent.

Stream B owns all algorithms that read this file. Streams A and C read it via Stream B's loader.

## Documentation — required, not optional

Three documents, three cadences. Write them while you work, not retrospectively.

### 1. Worklog — `doc/worklog/STREAM-{A,B,C}-log.md`

**When:** at the END of each phase (not per commit).
**Who:** the stream that owns the log file.
**Format:** see `doc/worklog/README.md` — copy-paste the template.
**Content:** what was built (1 paragraph), why (non-obvious decisions only — skip if none), how (only for complex phases), contracts emitted to other streams, follow-ups, tests.
**Length:** under 300 words per entry.

Append only. Never edit or reorder prior entries — they're the historical record.

### 2. Decisions — `doc/DECISIONS.md`

**When:** at the moment you make a non-obvious decision that affects multiple streams, involves a real trade-off, or that future-you would regret without context.
**Who:** any stream.
**Format:** see the template at the top of `DECISIONS.md`. Numbered `[YYYY-NN]` IDs for stable cross-references.
**Content:** Context, Decision, Consequences, Alternatives considered.

Never delete or rewrite. If a decision is reversed, add a new entry marking the old one as superseded.

### 3. Architecture — `doc/ARCHITECTURE.md`

**When:** when a phase introduces a new system-level pattern (e.g. a new cross-cutting module, a new data flow, a new serving path). Not for every internal implementation detail.
**Who:** whichever stream introduced the pattern.
**Content:** Update or add a section. Keep it narrative — readers should understand how pieces fit, not read a file list.

Your worklog entry should link to any ARCHITECTURE section you added: "Introduced photo-marker pattern — see ARCHITECTURE.md §Photos".

### Why this matters

Six months from now someone — possibly the operator, possibly a new engineer, possibly you on a future session — will ask "why is the renderer emitting placeholder markers instead of URLs?" Git log answers "what changed." These three documents answer **why** and **how**. Git is a transcript; these are the narrative.

### Quality bar

- Write the same day you finish the phase. Forgetting why is fast.
- Skip empty sections — don't pad a worklog entry to hit a word count.
- If a decision affects more than one stream, it goes in DECISIONS.md, not just a worklog.
- If a pattern will outlive the current phase, it goes in ARCHITECTURE.md too.
