# VI-006: Database Schema and Supabase Clients

## Summary
Provide the SQL migration the user runs in Supabase, define the
Storage-bucket requirements, and build the browser and server Supabase
clients.

## Background
Supabase is our backend for everything: Postgres for data, Auth for
users, Storage for the generated HTML. RLS is essential — couples
must only see their own data, and the RSVP `INSERT` policy must be
public so guests can submit without accounts.

## Work Required
- `supabase/migrations/001_init.sql` with:
  - `couples`, `events`, `rsvps`, `site_versions` tables.
  - RLS enabled on all four.
  - Policies: owner access on couples/events/site_versions,
    `SELECT` by owner on rsvps, public `INSERT` on rsvps.
- A Storage bucket named `wedding-sites` (public, 5MB limit) — created
  in the Supabase dashboard since we cannot run that via SQL.
- `src/lib/supabase/client.ts` — browser client via `@supabase/ssr`.
- `src/lib/supabase/server.ts` — server client bound to cookies; plus
  a `createServiceRoleClient()` for the public `/w/[slug]` route.

## Technical Notes
The SQL file is under `supabase/migrations/` so it's easy to find and
re-run. The "Coming soon" behaviour on unpublished sites uses the
service-role client because the slug lookup has to work without a
logged-in user.

## Acceptance Criteria
- [x] `supabase/migrations/001_init.sql` contains all four tables
      and all five policies.
- [x] `src/lib/supabase/client.ts` exports `createClient()`.
- [x] `src/lib/supabase/server.ts` exports `createClient()` (cookies
      bound) and `createServiceRoleClient()`.
- [x] Both clients use the env vars correctly.

## Dependencies
VI-001.

## Definition of Done
Running the migration in the Supabase SQL editor creates all tables
and policies without errors.
